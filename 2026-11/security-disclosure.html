Core discloses easy-to-find bugs sooner

Bitcoin Core runs Bitcoin nodes. Developers normally publish a security fix before describing the flaw, giving operators time to update.

THE DISCLOSURE CHANGE
  • Bugs found with little effort, including a simple request to an AI model, now get fixes for supported releases and prompt public explanations.
  • The normal delay is longer: low severity waits two weeks after a fixed major release; medium/high waits until two weeks after support ends for the last affected release.
WHAT THIS BATCH FIXES
  • Two medium-severity bugs keep storing network data until the node runs out of memory and can crash.
  • Nodes keep undo records to reverse blocks when switching to another chain branch. A low-severity bug can corrupt oversized files holding those records.

Fixes: Core 29.5, 30.4, 31.2 and 32.1, released 27–28 October. The undo-file issue remains on 32-bit systems and FAT32 disks. Core 29.x will receive no further updates.

A peer could bypass Core’s receive limit

Bitcoin nodes receive blocks and transactions from other nodes, called peers. Core queues that data until it can process it.

HOW THE LIMIT WAS BYPASSED
  • If a peer’s queue gets too large, Core pauses reads from that connection to limit memory use.
  • The TCP connection has a separate urgent-data signal. Core watched for it even while normal reads were paused.
  • The code handling that notification kept reading data. Repeating it grew the queue without limit and could crash the node.
THE FIX AND AFFECTED SYSTEMS
  • Only watch that notification while the connection is allowed to read.
  • The affected network code runs on Windows, macOS and BSD. Linux uses a different path and was unaffected.

Spiral’s automated scanner Project Loupe found CVE-2026-117350 on 23 October. Gregory Sanders validated it; the fix merged on 26 October.

BTCPay fixes isolation between merchants

BTCPay Server lets merchants run their own Bitcoin checkout. One installation can host separate stores for several merchants.

ONE STORE AFFECTING ANOTHER
  • For Lightning payments, a store’s node reports which invoice was paid. BTCPay must match that report to the correct store and invoice.
  • Store A’s Lightning node could report Store B’s payment hash, the invoice’s payment identifier, and block B’s payment processing.
  • The fix rejects notifications whose hash does not match the expected invoice.
INVOICE DATA EXPOSURE
  • The interface for BitPay-compatible apps allowed anonymous reads of individual invoices, exposing buyer information. The fix requires authentication.
  • Original scanner ratings: 1 critical, 13 high, 52 medium, 19 low.

Version 2.4.7, released 29 October, fixes 85 findings from Anthropic’s scanner. Some expose data or interrupt payments; they do not all permit theft.

BTCPay 2.4.7 release notes Cross-store payment fix #7758

Older BTCPay servers suffered wallet thefts

Some merchants keep their spending keys on the BTCPay server itself. These online wallets are called hot wallets.

THE PATCH WAS ALREADY AVAILABLE
  • BTCPay’s 2 November report identifies victims running 2.4.1 or earlier. Version 2.4.2 fixed the flaw on 7 August.
  • The attacks used another way to exploit that old flaw. Wallets whose spending keys stayed off-server were unaffected by these thefts.
RECOVERY AFTER COMPROMISE
  • BTCPay advises creating a wallet with new recovery words on a trusted device and moving remaining funds.
  • Take the old server offline, build a fresh server and replace exposed passwords and access keys.
  • Do not restore the compromised machine wholesale.

A software update does not undo a copied key or stolen password. This incident is separate from the 85 findings fixed in 2.4.7.
