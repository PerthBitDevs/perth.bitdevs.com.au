Eltoo changes how payment channels close

A payment channel locks bitcoin on-chain. Participants exchange signed balance updates without publishing every payment.

OLD AGREEMENTS STILL EXIST
  • Alice and Bob lock 100,000 sats and agree 60,000 / 40,000. Alice pays Bob; they now agree 40,000 / 60,000.
  • Each agreement is a channel state. The old signed state still exists and would pay Alice too much.
  • Today’s Lightning channels use a penalty: publishing a revoked state lets the other party claim the channel funds.
ELTOO: REPLACE THE OLD AGREEMENT
  • Eltoo is a proposed channel update protocol. A newer signed state can replace an old state published on-chain.
  • Payout waits through a challenge period, giving the other party time to submit the newer state.
  • The channel then pays the latest agreed balances, without the stale-state penalty.

Participants or a monitoring service must still detect the old state and get the newer update confirmed before the old payout becomes valid.

Eltoo: channel design and security model

A test channel replaces an old balance

Aaron Zhang’s 31 October demonstration runs on Inquisition signet, an experimental Bitcoin test network.

It separates the transaction that updates the channel state from the transaction that settles it, paying coins to the participants.

StepWhat happens on the test network
1. Publish the old stateUpdate transaction U1 creates an output holding the channel coins under the earlier agreement.
2. Override itThe newer signed update U3 spends that output. It skips intermediate update U2.
3. Pay outSettlement for state 3 divides the coins into 40,000 / 35,000 / 25,000 sats.

U3 was signed before any state output existed, yet could later spend U1’s output. One key stands in for all participants in this toy demonstration.

Experiment and signet transactions BIP446: template commitments Eltoo channel design

Sign an update before knowing its input

Ordinary signatures name a specific earlier output. Eltoo updates must work with different old states.

A transaction template fixes selected fields, including the new channel output and state number. Its hash fingerprints those choices while leaving out the exact earlier output.

The proposed Script instructions used by the experiment
InstructionIts job
TEMPLATEHASHCompute that fingerprint from the transaction attempting to spend the channel coins.
CHECKSIGFROMSTACK (CSFS)Check that the channel key signed that fingerprint, authorising the new state.
INTERNALKEYRetrieve the channel signing key chosen when this Taproot output was created.

State numbers go in the transaction’s locktime field. Bitcoin’s existing CLTV instruction checks the output’s minimum accepted number, preventing old states from replacing newer ones.

WHAT WAS DEMONSTRATED
  • A pre-signed update overrides an old state. Computing the template hash removes an extra copy previously supplied with the spend.
WHAT THIS DOES NOT YET TEST
  • Independent participants and their signing or recovery procedures.
  • Conditional payments for routing through Lightning, known as HTLCs.

These measurements are not production Lightning benchmarks. The proposed instructions still need activation before Bitcoin mainnet use.
