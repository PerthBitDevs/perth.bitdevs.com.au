Silent Payments Are Back In The Room

BIP-352 is Complete, Sparrow 2.5.x adds initial receiving support, and 2140 reports ongoing SP work

DRAFT TAKEAWAY
Silent Payments give receivers a static payment address without asking senders to put notification data on-chain. The cost is shifted into wallet scanning, recovery, and light-client design.
SPEC STATUS
BIP-352 is an Applications-layer specification for static Bitcoin payment addresses without on-chain linkability or on-chain notifications.
WALLET SIGNAL
Sparrow 2.5.0 adds Silent Payments receiving wallets, including support for airgapped hardware wallet signers.
2140 SIGNAL
2140's first annual report says its team worked on Silent Payments integration in Bitcoin Core and libsecp256k1, and hosted a Silent Payments gathering in Amsterdam.
COMMUNITY SIGNAL
Issue #36 raised Sparrow's release as a topic, which is why this is split out from the general roundup.

The Problem It Tries To Solve

Reusable identifiers without reusable on-chain addresses

ADDRESS REUSE
A normal static address is easy to share but leaks linkage when reused. Fresh addresses avoid that, but require interaction or infrastructure.
NOTIFICATION SCHEMES
Protocols can use on-chain notifications, but that creates extra cost and a recognizable footprint that can leak metadata.
SILENT PAYMENTS
The receiver publishes a reusable Silent Payment address. Each payment still lands in a unique Taproot output that does not reveal the static address.
TRADEOFF
The receiver has to scan eligible transactions to find payments. BIP-352 treats light-client support as an open research area.

How v0 Works, Simplified

One shared secret, one tweaked Taproot output, no notification output

01
Receiver publishes keys
A Silent Payment address encodes a scan public key and a spend public key.
02
Sender derives a tweak
The sender combines their input keys with the receiver scan key to derive a shared secret.
03
Output looks ordinary
The payment is a BIP-341 Taproot output to a tweaked key, not a marked notification transaction.
IMPORTANT DETAIL
BIP-352 v0 uses all eligible inputs for shared-secret derivation. This reduces receiver scanning work and avoids revealing one chosen input to the receiver in collaborative transaction settings.

Wallet Reality

The protocol shape is elegant, but implementation lives in the scanning details

SCAN / SPEND SPLIT
The receiver can keep spend keys offline while exposing a scan key to an online device that searches for incoming payments.
RECOVERY
Wallets need reliable scan history, descriptors, labels, and backup behavior so funds are found again after restore.
PUBLIC SERVERS
Sparrow 2.5.0 notes an SP-capable public Electrum server and automatic selection when required.
LIGHT CLIENTS
BIP-352 says private light-client support is possible but remains an area of open research.
